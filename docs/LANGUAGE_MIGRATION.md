# English migration and compatibility

The English migration covers all eleven Module directories, their source
builders and composers, the Company in a Box template, documentation, and
user-facing text produced by Workflows and MiniApps. Generated files must be
rebuilt from their corresponding sources. Runtime qualification is separate
from source and offline test results.

## Terms and stable identifiers

| Display term | Existing technical identifier or value |
|---|---|
| Watch | `veille`, `cib-veille` |
| Content | `contenu`, `cib-contenu` |
| Support | `accompagnement`, `cib-accompagnement` |
| Work case | `cib-work-dossiers`, `cib-cases` |
| Shared memory | `company-memory` |
| Manual confirmation | `confirmation_manuelle`, `oui`, `non` |

The right column consists of existing IDs, wire keys, namespaces or values;
it is not a translation table for user data. Preserve them, and preserve
historical fixtures and fingerprints. Translate labels, help text, descriptions,
prompts and messages without translating records entered by users. Changing a
wire contract requires a separately versioned contract, a mapping and an
old/new round-trip test.

A changed published Module is assigned a new package version; a changed
Workflow or MiniApp receives a new native version, with references updated.
Keep historical package bytes and hashes available through their original
revisions. Consumer-specific generated resources also need their own distinct
versions; for example, the `daily-context` consumer variant must not share an
ID and version with a different Module resource. Preview upgrades and reject
unknown divergence rather than overwriting consumer changes.

The common governed Agent instructions, `NOTICE`, and historical test
fixtures are not product translations. Their exclusion does not exempt user
interfaces, generated text or documentation from review.

## Coverage matrix and review procedure

`inventory/modules.json` is the file-level matrix: it is generated by walking
every `*/module.yaml` without a numeric ceiling and records each Workflow,
MiniApp, generator and composer. Review all rows and each generated resource,
including embedded code, instead of sampling only manifests:

| Module | Source and consumer scope |
| --- | --- |
| `company-memory` | Direct resources and `tooling/company-memory` |
| `cib-veille`, `cib-contenu`, `cib-accompagnement` | Direct role resources, role tests and CIB composer |
| `cib-veille-memory`, `cib-contenu-memory`, `cib-accompagnement-memory` | Direct resources and `tooling/memory-integration` bridges |
| `cib-daily-routine` | `tooling/daily-routine` builder, metrics, consumer variants and generated resources |
| `cib-work-dossiers` | `tooling/work-cases` builder, domain and generated resources |
| `cib-enterprise-admin` | `tooling/enterprise-admin` builder and generated resources |
| `cib-marketing-launch` | `tooling/marketing-launch` builder, domain, runtime, test plan and generated resources |
| Company in a Box template | `templates/company-in-a-box` configuration, surface, composer, plans and tests |

Run `python3 scripts/language_audit.py` to list candidate lines, including
embedded code. It is a screening heuristic, not a language detector: English
may contain its terms and French without those terms may be missed. A reviewer
must inspect every matrix row, display path and generated message, including
form labels, summaries, empty states, errors and tables. A technical exception
must identify the exact content and reason; a whole product file cannot be
exempted merely because it contains stable identifiers. `--check` is a strict
candidate gate. Individually reviewed technical exceptions are listed by path
and exact line hash in `scripts/language_exceptions.json`; stale exceptions
fail the gate. The presence of a green
heuristic alone does not establish complete English coverage.
